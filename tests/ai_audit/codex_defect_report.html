Что является блокером production

  • SQL Server: любой запуск до исправления staging DDL и identity-семантики.
  • MySQL/MariaDB: любой запуск с can_create_table=True или can_create_columns=True для строк, float и datetime.
  • MySQL: любой integer key, в котором допустим 0, даже при заранее созданной target-таблице.
  • PostgreSQL: автосозданная integer-key таблица, если после merge ожидаются обычные вставки с default sequence.
  • Все СУБД: full-snapshot с перераспределением значений под обычным UNIQUE, source-table с generated columns и входные данные без строгой проверки схемы.

Что в этом отчёте не названо багом

  • Пустой dataset при delete_mode='delete' очищает target. Это заявленная семантика полного снимка.
  • Пошаговые commit по умолчанию являются осознанным компромиссом ради размера транзакции/WAL. Частичный результат после поздней ошибки здесь не переименован в дефект.
  • Уникальность merge-key и конкурентный доступ должны обеспечиваться схемой и транзакционной политикой БД.
  • Но БД не отвечает за staging, который модуль сам ошибочно делает AUTO_INCREMENT/IDENTITY, за неверный тип DECIMAL(10,0) или за порядок DML, не способный достичь валидного конечного состояния.

3. P0: блокеры и порча данных

DB-01. Float превращается в DECIMAL(10,0) и округляется

Полный паспорт воспроизведения: исходное состояние, типы и контроль результата

Контур. Основной запуск выполнен на MySQL 8.4.11, повторяющий запуск — на MariaDB 11.4.12. Это два отдельных запуска с отдельными именами target-таблиц; результат одной СУБД не переносился в другую.

Что существовало до вызова. Сама база и учетная запись существовали, но таблицы auto_float_2c2d1187 в MySQL и auto_float_c0e0704f в MariaDB отсутствовали. Это проверялось через каталог СУБД до вызова. Следовательно, до теста не существовали ни столбец amount, ни его SQL-тип, ни primary key, ни default/trigger, способные изменить значение. Источником была структура в памяти процесса, а не исходная SQL-таблица.

Точный вход и типы. В базовом варианте передавался один Python-record {"id": 1, "amount": 1.75}: id имел runtime-тип int, amount — float. Дополнительные независимые прогоны использовали Pandas DataFrame, где amount имел dtype float64, и Polars DataFrame, где этот столбец имел dtype Float64. Значение не поступало строкой "1.75" и не было заранее округлено приложением.

Параметры операции. Был включен штатный путь автосоздания target; ключом сопоставления служил id. Пользовательский data_types для amount намеренно не задавался: проверялось именно документированное автоматическое определение схемы. Таблица не подготавливалась вручную.

Как проходил тест. (1) Проверено отсутствие target. (2) DBMerge проанализировал входные значения и построил metadata target. (3) Модуль создал target и временную staging-таблицу. (4) Одна строка была загружена в staging и перенесена в target. (5) После завершения независимо прочитаны information_schema.columns и сама строка обычным SELECT. (6) Временные и target-объекты удалялись только после фиксации доказательств.

Фактический выход. В обоих серверных диалектах столбец был создан как DECIMAL(10,0). В target находилось числовое значение 2, а не 1.75: дробная часть была необратимо потеряна при записи. Та же ветка воспроизвелась для Python, Pandas и Polars, поэтому дефект не сводится к одному адаптеру входных данных.

Оракул и локализация дефекта. Проверялось round-trip равенство: значение после чтения должно быть численно равно входному 1.75. Оно не равно. Так как target и поле до запуска отсутствовали, изменение внесено цепочкой «инференс типа → сгенерированный DDL → запись», а не прежней схемой клиента. Ручное задание типа с ненулевым scale является обходом, но не исправляет опасный default автосоздания.

P0 DATA CORRUPTION LIVE MySQL + MariaDB

Как именно проводился тест

Состояние MySQL до запуска. Был поднят одноразовый MySQL Community 8.4.11 с пустой schema dbmerge_audit. Таблицы auto_float_2c2d1187 до теста не существовало. Не существовало и staging: её должен был создать сам DBMerge. SQL mode сервера содержал STRICT_TRANS_TABLES, то есть тест выполнялся не в ослабленном режиме.

Полный вход. В DBMerge передан Python-объект [{'id': 1, 'amount': 1.75}]. Параметры: table_name='auto_float_2c2d1187', schema='dbmerge_audit', key=['id']; can_create_table и can_create_columns оставлены в значении True, delete_mode='no'. Physical source table не было: source находился в памяти.

Ход. Конструктор определил типы id и amount. Во время exec() DBMerge создал target и временную staging с generated suffix, загрузил в staging одну строку, выполнил UPDATE для совпавших ключей и INSERT отсутствующих. После возврата success отдельным connection выполнены два независимых запроса: metadata из information_schema.columns и SELECT amount ... WHERE id=1.

Выход. Metadata показала COLUMN_TYPE='decimal(10,0)', precision=10, scale=0. SELECT вернул 2 вместо входного 1.75. Исключения и warning не было. После фиксации результата target удалена, container остановлен и удалён.

Независимый повтор. На MariaDB 11.4.12 таблица auto_float_c0e0704f также отсутствовала до теста; вход и параметры были идентичны. Результат снова decimal(10,0) и stored=2. На MySQL отдельно повторены отсутствующие target для Pandas DataFrame({'id':[1], 'amount':[1.75]}) и Polars с теми же значениями; обе ветки дали тот же DDL и read-back.

Сценарий. Target отсутствует, типы выводятся автоматически. Вход: {'id': 1, 'amount': 1.75}.

MySQL 8.4.11:
metadata = {NUMERIC_PRECISION: 10, NUMERIC_SCALE: 0,
            COLUMN_TYPE: "decimal(10,0)"}
input  = 1.75
stored = 2

MariaDB 11.4.12:
column_type = "decimal(10,0)"
input  = 1.75
stored = 2

Область. Повторено для Python list[dict], Pandas и Polars. Это общий type inference.

Корень. В src/dbmerge/dbmerge.py:732-803 float сводится к Numeric() без precision/scale. MySQL определяет голый DECIMAL как DECIMAL(10,0). См. MySQL Fixed-Point Types.

Исправление. Для Python float использовать dialect-aware double precision. Для Decimal требовать или вычислять явные Numeric(precision, scale). Regression должен сравнивать round-trip и metadata.

DB-02. Datetime теряет микросекунды и timezone

Полный паспорт воспроизведения: существование поля, Python/dtype и SQL-тип

Контур. Проведены независимые прогоны на MySQL 8.4.11 и MariaDB 11.4.12. Для каждой СУБД использовалась новая target-таблица и заново сформированный источник.

Что существовало до вызова. Таблица auto_dt_b740bd95 в MySQL отсутствовала. Таблица auto_datetime_e74ec74a в MariaDB также отсутствовала. Отсутствие проверялось по системному каталогу до запуска. Поэтому datetime-столбца до DBMerge не было вообще: у него не было заранее заданного DATETIME, precision, default, trigger или timezone-конвертации. Источник не являлся SQL-таблицей.

Точный вход и типы. В Python-варианте передавалась одна строка-словарь с целочисленным id и тем aware-значением даты/времени, полный ISO-литерал которого приведен в строке «Вход» этого кейса. Runtime-тип поля — datetime.datetime; tzinfo is not None; компонент microsecond ненулевой и равен 123456. То есть на входе одновременно присутствовали две проверяемые характеристики: дробная часть секунды и смещение часового пояса. В Pandas-контроле применялся timezone-aware datetime dtype, в Polars-контроле — Datetime с временной зоной; это были отдельные новые target-таблицы.

Параметры операции. Включено автосоздание target, ключ — id, явный SQL-тип datetime-поля через data_types не передавался. Тем самым тестировалcя именно default-инференс DBMerge, а не поведение заранее созданного пользовательского столбца.

Как проходил тест. (1) Каталог подтвердил отсутствие target и поля. (2) DBMerge определил тип из source object/dtype. (3) Сгенерировал и выполнил DDL target, затем создал staging. (4) Исходный timestamp был записан без предварительного преобразования тестом в строку или naive datetime. (5) После merge отдельно считаны metadata столбца — базовый SQL-тип, fractional-seconds precision — и значение через SELECT. (6) У считанного Python-значения отдельно сравнивались календарная часть, microsecond, tzinfo и UTC-offset.

Фактический выход. Автосоздание выбрало серверный DATETIME без fractional-seconds precision, то есть фактически fsp=0, и без сохраняемой timezone-семантики. После чтения microsecond == 0, а tzinfo is None. Секундная календарная часть сохранилась, но исходное значение целиком не сохранилось: микросекунды отброшены, aware datetime стал naive. Поведение повторилось на MySQL и MariaDB, а также не исчезло при смене Python-list на DataFrame-вход.

Почему это доказательство дефекта модуля. Ни таблицы, ни поля до теста не было; следовательно, клиентская DDL не могла задать недостаточную precision. Именно DBMerge выбрал тип при автосоздании. Драйвер возвращает то, что реально хранит созданный столбец, поэтому это не только косметика Python-представления. Для корректного round-trip модуль должен либо выводить тип с достаточным fsp и явной политикой timezone, либо отклонять aware datetime без явного типа, а не молча менять значение.

Граница доказательства. Тест доказывает потерю timezone-семантики и микросекунд в указанном пути автосоздания. Он не утверждает, что MySQL нативно умеет хранить timezone в DATETIME; напротив, обязанность библиотеки — выбрать безопасную нормализацию, подходящий тип/сопутствующее поле или явную ошибку. Ручной DDL может обойти проблему, но это иной режим.

P0 DATA CORRUPTION LIVE MySQL + MariaDB

Как именно проводился тест

Состояние БД. На MySQL 8.4.11 target dbmerge_audit.auto_dt_b740bd95 отсутствовала. На MariaDB 11.4.12 target dbmerge_audit.auto_datetime_e74ec74a также отсутствовала. В обоих случаях DBMerge должен был создать target и temporary staging полностью по входным Python types.

Полный вход. Одна строка: integer id=1 и aware Python datetime 2026-08-02 12:34:56.987654+03:00. Параметры DBMerge: schema=dbmerge_audit, key=['id'], auto-create включён, delete mode=no. Source table отсутствовала.

Ход. После exec() отдельным SELECT считано сохранённое время, а из information_schema.columns получены column_type и datetime_precision. То есть проверялось не строковое представление result, а реально созданная схема и значение на сервере.

Выход MySQL. Колонка создана как datetime с precision=0; сервер вернул 2026-08-02 12:34:57. Offset +03:00 отсутствует, 987654 microseconds округлены вверх.

Выход MariaDB. Колонка также datetime(0); сервер вернул 2026-08-02 12:34:56, то есть offset и дробная часть потеряны, но округление отличается от MySQL. Pandas и Polars проверялись в отдельных отсутствующих target: Pandas Timestamp с +03:00 и UTC-aware Polars datetime оба создали datetime(0).

input = 2026-08-02T12:34:56.987654+03:00
MySQL:   datetime(0) -> 2026-08-02 12:34:57
MariaDB: datetime(0) -> 2026-08-02 12:34:56

Корень. Generic DateTime(timezone=True) становится MySQL DATETIME без fsp. Default fractional precision равна 0, округление может пройти без warning: MySQL Fractional Seconds. DATETIME не хранит offset, а модуль не нормализует UTC.

Исправление. Использовать DATETIME(fsp=6). Для aware values зафиксировать контракт: UTC normalization либо явный reject на dialect без timezone type.

DB-03. SQL Server получает недопустимый CREATE TEMPORARY TABLE

Полный паспорт воспроизведения и уровень доказательства

Контур. Живого Microsoft SQL Server в тестовом окружении не было. Поэтому серверный результат не маркируется как live reproduction: использован SQLAlchemy MSSQL dialect compiler, то есть та же компиляция DDL, которую код DBMerge передал бы драйверу. Отдельный SQLite-запуск подтверждал, что входные данные и общая ветка merge работоспособны вне MSSQL-специфичного DDL.

Состояние до теста. В SQLite-контроле target items существовал заранее со столбцами id INTEGER PRIMARY KEY и value VARCHAR(50); исходные строки и source snapshot приведены непосредственно в кейсе. Runtime staging-таблицы до вызова не было. Во время выполнения код сгенерировал имя items_67353bd8. Для MSSQL-проверки никакая физическая таблица не создавалась: metadata существующей модели компилировалась в MSSQL SQL.

Вход и типы. Source состоял из records с id: int и value: str; ключом был id. Целевой id был целочисленным primary key. Именно наличие такого ключа существенно для второй части дефекта: SQLAlchemy считает его identity/autoincrement-кандидатом, и DBMerge переносит это свойство в staging.

Как проходил тест. (1) На контроле выполнена обычная подготовка target и merge. (2) Перехвачена metadata временной таблицы, которую строит DBMerge, включая имя и свойства столбцов. (3) Объект CreateTable скомпилирован MSSQL-диалектом без ручного переписывания SQL. (4) Проверены два независимых фрагмента результата: ключевые слова создания временного объекта и наличие IDENTITY у staging-ключа. (5) Затем результат сопоставлен с синтаксисом временных таблиц SQL Server и правилами явной вставки в identity-столбец.

Фактический выход. Получен SQL с CREATE TEMPORARY TABLE, который SQL Server не поддерживает для локальных temp tables, и одновременно staging-колонка получила IDENTITY. Даже после исправления первого фрагмента загрузка явных source-id в такую staging-таблицу потребует специального IDENTITY_INSERT либо отказа от identity. Это две самостоятельные точки отказа одного MSSQL-пути.

Что доказано и что не доказано. Доказано, что текущий код генерирует несовместимый MSSQL DDL до обращения к серверу. Не измерены конкретный номер server error и поведение конкретного ODBC-драйвера, поскольку live SQL Server отсутствовал. Для закрытия кейса после исправления нужен интеграционный тест на поддерживаемой версии SQL Server, но отсутствие live-инстанса не делает скомпилированный запрещенный синтаксис допустимым.

MySQL: тихая подмена 0

target before  = [(0, "zero-old"), (1, "one-old")]
delete_mode    = "delete"
target after   = [(1, "zero-new")]
status         = success

PostgreSQL: stale sequence

auto-created id default = nextval('..._id_seq'::regclass)
merged explicit ids     = 1, 2
next INSERT without id  = UniqueViolation on id=1

SQL Server

Staging key компилируется как IDENTITY, а явный insert отклоняется.

DB-06. UPDATE → INSERT → DELETE создаёт ложные UNIQUE-конфликты

Полный паспорт valid-snapshot под UNIQUE

Контур. Один логический сценарий воспроизведен на SQLite 3.49.1, PostgreSQL 18.3 и MySQL 8.4.11. Для каждой СУБД target создавался отдельно нативным DDL; результаты не эмулировались одной СУБД.

Состояние до запуска. Target существовал. В нем были целочисленный primary key id и отдельный бизнес-столбец с ограничением UNIQUE. До merge находились две строки: одна владела уникальным значением, которое по входному snapshot должно перейти другой строке; прежняя строка-владелец в source отсутствовала и потому подлежала удалению. Staging до вызова отсутствовал. Точный DDL, исходные строки и target names приведены в теле кейса.

Вход и типы. Source — валидный конечный snapshot: Python records с id: int и уникальным атрибутом строкового типа. В самом source дубликата нет; ожидаемая конечная target также не содержит дубликата. Ключ сопоставления — id; включено удаление target-строк, отсутствующих во входном snapshot.

Как проходил тест. (1) До запуска запрос подтвердил обе исходные строки и действующее UNIQUE-ограничение. (2) Source загружен в staging. (3) DBMerge начал применять изменения в порядке update/insert до удаления obsolete target-row. (4) Попытка присвоить новой строке еще занятое уникальное значение встретила действующее ограничение. (5) Зафиксированы server exception и фактическое состояние target после обработки/rollback. (6) Контрольный вариант с безопасным порядком освобождения значения показал, что сам конечный snapshot допустим.

Фактический выход. Все три СУБД отвергли промежуточное, а не конечное состояние, с unique-violation. Требуемый snapshot не был применен, хотя он удовлетворяет constraint. Это не спор о том, должна ли БД обеспечивать уникальность: БД именно правильно ее обеспечивает; ошибка модуля — порядок построения промежуточных состояний.

Постусловие. В отчете отдельно указано, была ли транзакция откатана и какие строки остались после каждого engine-specific запуска. Критерий исправления: алгоритм должен уметь применить валидное конечное множество без временного нарушения UNIQUE — например, планированием delete/update, deferrable constraint там, где доступно, либо двухфазной заменой с документированными ограничениями.

Как именно проводился тест

PostgreSQL: UniqueViolation

DB-11. SQLite :memory: с NullPool теряет target

Полный паспорт SQLite :memory: + NullPool

Состояние до запуска. Создан новый engine для sqlite:///:memory: с явным NullPool. Target отсутствовал; поскольку это in-memory SQLite, сама база также существует только в пределах конкретного DBAPI-соединения. Source — одна in-memory record с целочисленным ключом и простым значением. Никакой файловой SQLite-БД или заранее созданной таблицы не было.

Почему pool — часть входных условий. NullPool закрывает соединение после использования и выдает новое при следующем checkout. Для :memory: это уже другая пустая БД. Этот engine валиден для SQLAlchemy; тест проверяет, удерживает ли одна логическая операция DBMerge единое соединение.

Как проходил тест. (1) DBMerge начал merge и на одном checkout выполнил создание/проверку объекта. (2) Между следующими фазами соединение было возвращено/закрыто. (3) Следующий checkout получил другую in-memory database. (4) Последующий DDL/DML обратился к target или staging, которой в новом соединении нет. (5) Зафиксированы exception и отсутствие устойчивой итоговой таблицы. (6) Контрольный запуск с сохраняющим одно соединение штатным SQLite pool прошел на том же наборе данных.

Фактический выход. Логически единый merge распадается между физическими базами и завершается no such table. Ошибка не связана с именем поля или source value. Она показывает, что операция не закрепляет connection scope, хотя временные таблицы, транзакции и in-memory БД семантически connection-local.

Область риска. Минимальное воспроизведение — SQLite :memory: + NullPool, но архитектурный риск шире: разные checkout могут менять видимость temp objects и транзакционную целостность. Исправление — выполнять один merge через одно явно удерживаемое connection/transaction либо запретить несовместимую конфигурацию до DDL.

Как именно проводился тест

На нём target никогда не существовала. Выход: OperationalError: no such table: nullpool_case. Control с обычной file SQLite и корректным shared connection не демонстрирует эту ошибку.

DB-12. Cleanup способен скрыть primary error

Полный паспорт первичной ошибки и cleanup-failure

Два уровня проверки. Основной тест — контролируемая fault injection, позволяющая гарантированно получить две разные ошибки в заданном порядке. Отдельный PostgreSQL-контроль использует настоящее CHECK-ограничение и показывает реальный класс первичных server failures. Эти доказательства не смешиваются.

Состояние основного теста. Target и минимальная схема были подготовлены так, как указано в кейсе; staging до вызова отсутствовал. Source содержал строку, достаточную для входа в mutation path. Первая точка была заменена детерминированным исключением A, cleanup/drop — другим исключением B. Типы, сообщения и место обеих инъекций приведены в подпункте теста.

Как проходил fault-injection тест. (1) Запуск доведен до основной операции. (2) В основной фазе выброшено A; оно сохранено тестовым harness как первопричина. (3) Выполнение вошло в finally/cleanup. (4) Удаление staging выбросило B. (5) Вызывающий код получил исключение; сравнивались его type/message, __cause__/__context__ и сохранность A. (6) Отдельно зафиксировано состояние target/staging после двойного отказа.

Фактический выход. Наружу выходит cleanup error B, а диагностически важная первичная ошибка A маскируется. Оператор видит проблему удаления временного объекта вместо причины, по которой merge не применил данные. Это усложняет retry: по внешней ошибке нельзя надежно определить, была ли mutation частично выполнена.

PostgreSQL-контроль. Заранее созданная таблица имела реальное CHECK-ограничение; source содержал значение, нарушающее его. Merge дошел до server DML и получил constraint violation. Этот прогон подтверждает, что первичные ошибки такого класса естественно возникают без monkeypatch; fault injection нужна только для воспроизводимого одновременного отказа cleanup.

Оракул. Первичная ошибка должна оставаться основной; cleanup-failure следует присоединять как cause/note, логировать отдельно или агрегировать, но не подменять им исходную причину. В отчете отдельно указаны таблицы и постсостояние для обоих запусков.

Как именно проводился тест

Это fault-injection test, а не имитация конкретной СУБД. В тестовом экземпляре DBMerge основной исполнитель заменён функцией, которая выбрасывает ValueError('PRIMARY_FAILURE') после создания staging. Cleanup staging заменён функцией с RuntimeError('CLEANUP_FAILURE'). Target имела минимальные id/payload columns.

Oracle: наружу должен выйти PRIMARY_FAILURE, cleanup failure должен быть сохранён как context/note, connection обязан закрыться в любом случае. Факт: наружу вышел CLEANUP_FAILURE, connection_closed=false, merge_finished=false.

Контроль области. На PostgreSQL 18.3 отдельно создана session-temp target id bigint PK, value text CHECK(length(value)<=3). Source передал 'too-long'; staging не имела CHECK, поэтому нарушение произошло именно при target INSERT. В этом обычном DB error case исходный IntegrityError/CheckViolation сохранился, connection закрылся. Поэтому finding относится к двойному отказу cleanup, а не ко всем constraint errors.

Fault injection: primary stage выбрасывает PRIMARY_FAILURE, drop temp выбрасывает CLEANUP_FAILURE. Наружу выходит cleanup error, connection_closed=false, merge_finished=false. Живой PostgreSQL CHECK violation этот дефект не воспроизвёл, поэтому это P2 robustness, а не частое DB-поведение.

Исправление. Guaranteed close во внешнем finally; cleanup error прикреплять к primary exception, не заменять его.

DB-13. total_time и “exact SQL” не соответствуют документации

Полный паспорт измерения времени и сопоставления SQL

Timing setup. Использовался минимальный merge одной строки; состояние target, ее DDL и входная record приведены в кейсе. К engine/connection были подключены счетчики событий. Перед каждым фактическим commit тестовый hook делал детерминированную задержку 40 ms. Зафиксировано шесть commit events, то есть только искусственная commit-задержка составляет около 240 ms, не считая SQL и Python-кода.

Как измерялось. (1) Непосредственно перед публичным вызовом снимался monotonic wall-clock. (2) Выполнялся merge без изменения его кода. (3) Hook считал каждый commit и задерживал именно commit, а не statement execution. (4) После возврата снимался wall-clock. (5) Из результата DBMerge извлекалось опубликованное total_time. (6) Сравнивались wall duration, сумма искусственных задержек и reported duration. Один record выбран, чтобы объем данных не маскировал разницу.

Фактический выход. Реальный вызов включил все шесть задержек, но total_time их не включил либо включил не полностью, потому что таймеры охватывают SQL-фрагменты, а пошаговые commits находятся за их границами. Поэтому метрика систематически занижает latency именно при режиме частых commit, который позиционируется как защита от накопления WAL.

Отдельный paramstyle-подтест. Это независимый тест, а не продолжение timing run. Один и тот же смысловой SQL был представлен в формах, которые драйвер/SQLAlchemy сериализует по-разному: placeholder style и/или текстовые различия не меняют операцию, но меняют строку. Механизм учета сопоставлял exact SQL text, поэтому start/finish не связались корректно. Точные строки, входные параметры и наблюдаемый результат приведены в подпункте.

Оракул и значение. total_time публичной операции должен измерять ее wall latency либо быть честно переименован в сумму ограниченных SQL-intervals. Для statement metrics нужен устойчивый execution context/correlation id, а не текстовое равенство SQL. Это observability-дефект: данные могут быть корректны, но SLO, capacity planning и расследование зависаний получают ложные цифры.

Как именно проводился тест

Timing case. Новая SQLite in-memory DB, target отсутствовала, source содержал одну строку id/value. На engine установлен SQLAlchemy commit event listener: перед возвратом каждого commit он выполнял sleep 40 ms и увеличивал счётчик. SQL case. В отдельном SQLite merge с existing target и source, вызывающим UPDATE/INSERT/DELETE, сохранены result insert_sql/update_sql/delete_sql. В insert template присутствовал named bind :id_1; dialect engine сообщил paramstyle='qmark'. Тест не утверждает, что логика statement неверна; проверялось только документированное слово exact.

DOCUMENTATION.md:129 называет total_time временем всей DB operation; строки 137-139 называют SQL exact. Фактически total складывается из DML timers (src/dbmerge/dbmerge.py:571-572) и не включает init, DDL, commit и cleanup.

wall time         = 0.248019 s

Что фиксировалось на входе. Для каждого подпункта непосредственно рядом приведены: форма source, число records, имена и runtime-типы ключей, точные значения опций, наличие/отсутствие target и поля, а также ожидаемая фаза отказа. Пустой dataset отдельно не трактуется как ошибка сам по себе: документированная семантика «пустой source + delete = опустошить target» сохранена и не записана в баг.

Как проходил каждый тест. (1) Проверялось предусловие target. (2) Создавался ровно один невалидный или пограничный input/config. (3) Вызывался публичный API. (4) Записывались exception class, message и наличие exception chaining. (5) Проверялось, был ли выполнен DDL/DML до обнаружения проблемы. (6) Если таблица существовала, считывалось ее постсостояние. Такой порядок отличает безопасный ранний отказ от поздней внутренней аварии после побочных эффектов.

Фактический общий результат. В перечисленных подпунктах библиотека выпускает наружу низкоуровневые KeyError, AttributeError, dialect/compiler errors или неоднозначные сообщения вместо стабильной ошибки контракта. Конкретный output и состояние таблицы после каждого варианта находятся в самом подпункте, а не вынесены в общую матрицу.

Критерий исправления. Ошибки структуры source и конфигурации должны выявляться до создания staging и до mutation target. Сообщение обязано назвать параметр/поле и нарушение; документированная destructive-семантика пустого snapshot должна остаться явной и тестироваться как положительный сценарий, а не «исправляться» запретом удаления.

Как именно проводились тесты

source_schema без source table. Конструктору передан source_schema, но source_table_name=None. Oracle требовал parameter validation до обращения к БД и IncorrectParameter. Фактически код попытался собрать полное имя с None и вернул raw TypeError. Таблица для воспроизведения не требовалась.

Конфликт managed names. В новой SQLite DB передано одинаковое имя для merged_on_field и inserted_on_field вместе с обычной source row. Oracle - reject конфликтующих ролей до DDL. Факт - raw AttributeError с is_sequence.

Нестрогий bool. В новой SQLite DB создан обычный merge с одной строкой; до exec() присвоено merge.commit_all_steps='false'. Commit listener считал события. Строка была принята как truthy, операция завершилась и вызвала пять commit events. Oracle - reject значения, тип которого не bool.

6.3. Production-риски

  • Телеметрия. Network commit latency может доминировать, но result.total_time её скрывает.
  • Крупные фазы. Пошаговый commit уменьшает общий transaction scope, но один массовый UPDATE/INSERT/DELETE всё равно может создать большой WAL/undo. Это предел стратегии, а не отрицание выбранного дизайна.
  • Staging statistics. Для большого PostgreSQL batch следует измерить ANALYZE temp; немедленный запрос может планироваться без репрезентативной статистики.
  • Индексы. PK staging создаётся; индекс/unique на target merge-key остаётся DB prerequisite.
  • Hot DDL. Automatic ALTER может брать metadata locks и не должен быть частью обычного production merge path.

7. Безопасность

7.1. Проверено без finding

  • Инъекционные target/helper identifiers проверены на SQLite и PostgreSQL. Sentinel tables сохранились; malicious-name table удалена корректно.
  • Bandit: 0 high, 0 medium, 2 low. Low относятся к подавлению исключений в destructor.
  • pip-audit обязательных runtime dependencies: известных уязвимостей нет.
  • Прямой SQL injection в проверенных identifier paths не подтверждён.

7.2. Hardening gaps

  • При аудите всех extras mariadb 1.1.14 отмечен PYSEC-2026-217 / CVE-2026-44172. Условия связаны с Big5/text protocol/manual escaping; обычный bound SQLAlchemy path не доказан уязвимым. Нужен upgrade/constraint и отдельная проверка.
  • GitHub Actions используют tags без pin на commit SHA; checkout credentials сохраняются; permissions шире минимальных. Это supply-chain risk, не runtime injection.
  • Auto-DDL требует повышенных прав. Production должен разделять migrator role и runtime merge role.

7.3. Почему auto-create сейчас небезопасен

Не сам автоматический DDL является дефектом. Дефект в том, что модуль выбирает physical type, precision, timezone, generated semantics и staging structure без полного dialect contract. Live-тесты показали три вида ущерба: DDL не компилируется, данные молча меняются, sequence/identity создаётся с неверной семантикой.

9. План исправления

Фаза 0. Production guards

  1. Для MySQL/MariaDB запретить auto-create/auto-add без explicit dialect-safe data_types.
  2. Для SQL Server fail-fast до появления рабочей staging implementation.
  3. Для MySQL временно запретить integer key 0.
  4. Для PostgreSQL проверить sequence уже автосозданных таблиц контролируемой миграцией.
  5. До DBMerge валидировать одинаковый key set dict rows и unique DataFrame columns.
  6. Исключить generated/computed fields из payload.

Фаза 1. Модель колонок

  1. Разделить source type, target DDL type и staging DDL type.
  2. Staging: копировать physical type, но снимать Identity, Sequence, Computed, defaults и autoincrement.
  3. Target merge-key: externally assigned PK по умолчанию.
  4. Float: dialect double; Decimal: explicit precision/scale.
  5. MySQL/MariaDB datetime: fsp=6 и timezone policy.
  6. String: configurable policy, explicit length для key/indexed fields.

Фаза 2. SQL Server adapter

  1. Session-local #temp, одна physical connection.
  2. Staging key без IDENTITY.
  3. Policy target identity: reject, omit generated id или контролируемый IDENTITY_INSERT.
  4. Live tests на поддерживаемых SQL Server и pyodbc.

Фаза 3. UNIQUE-safe snapshot

  1. Preflight values, занятых удаляемыми строками.
  2. В atomic mode рассмотреть delete-obsolete-before-upsert после FK preflight.
  3. Для swaps реализовать двухфазную стратегию либо fail-fast до изменения данных.
  4. Тестировать immediate и deferrable constraints.

Фаза 4. Input/API contract

  1. Strict row schema validation до DDL.
  2. Reject duplicate labels Pandas.
  3. Проверить конфликт ролей key/delete mark/merged-on/inserted-on.
  4. Managed data_types хранить отдельно от source fields.
  5. Перевести parameter failures в public domain exceptions.

Фаза 5. Release gate

  1. True wall-clock и stage/commit/DDL timings.
  2. Statement template вместо “exact SQL”.
  3. Устранить overwrite теста; фиксировать collection count.
  4. Live CI: PostgreSQL, MySQL, MariaDB, SQL Server, SQLite pool variants.
  5. Release запрещён без round-trip type и negative edge suite.

13. Итог

Основная идея проекта - компактный set-based merge через staging - подтверждается happy-path тестами. Production-риск находится не в полном снимке и не в пошаговых commit, а в неразделённой модели типов и колонок между Python, target и staging, а также в отсутствии dialect-specific DDL.

Приоритет: generated semantics ключей, типы MySQL/MariaDB, SQL Server staging, затем UNIQUE-safe snapshot и строгая валидация входа. До этого auto-DDL и SQL Server нельзя считать production-ready.

Отчёт основан на локальном коде, документации проекта, статье Habr, live negative tests и официальной документации СУБД. PostgreSQL objects были session-temporary; Docker containers удалялись после сценариев. Исходный код DBMerge не изменялся.
