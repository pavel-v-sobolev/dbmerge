## Контекст

Рассматриваемый общий сценарий: приложение подключает `dbmerge.MartHandler`
к уже заполненным таблицам, но новый журнал ещё не содержит записей об их
изменениях. При отсутствии watermark цикл может создать строки аренды,
но не начать первоначальную пересборку. Таблица `dbmerge_marts` при этом
может оставаться пустой.

Строки аренды с `owner = NULL` и `scope = NULL` обозначают свободные строки,
а не получение аренды. Неизменный heartbeat такой строки не означает зависание.
Явный `request_rebuild()` позволяет обойти ожидание сигнала источника.

## P2-1. Новая витрина ожидает изменения источников вместо первоначальной сборки

### Текущее поведение

В `MartLoop._run_pass()` отсутствие сохранённого watermark уже классифицируется
как полная пересборка:

```python
full_rebuild = stored_watermark is None or explicit_rebuild
```

Однако проверка изменений источников пропускается только для **явного** запроса
или сохранённого курсора:

```python
if not explicit_rebuild:
    if not full_rebuild and next_watermark <= watermark:
        return False
    if not self._sources_changed(watermark):
        return False
```

Поэтому при отсутствии watermark, курсора и запроса, а также отсутствии записей
об изменениях источников в новом журнале, цикл возвращает `False` до получения
аренды и вызова обработчика. Уже существующие данные источника сами по себе
не инициируют расчёт.

### Рекомендация

Отсутствие watermark должно означать первоначальную пересборку без зависимости
от наличия change-сигнала. Проверки «граница продвинулась» и «источники изменились»
нужны для обычного инкрементального прохода:

```python
if not full_rebuild:
    if next_watermark <= watermark:
        return False
    if not self._sources_changed(watermark):
        return False
```

Это рекомендуемая замена условия в существующем методе, а не готовый патч
всего lifecycle. Сохранить вычисление безопасной границы, получение аренды,
повторную проверку watermark/курсора/токена после получения аренды и защиту
фиксации прогресса. Не запускать запись из конструктора.

### Ожидаемая семантика

| Состояние | Действие |
|---|---|
| Нет watermark, нет change-сигналов | Первоначальная полная пересборка |
| Нет watermark, источник пуст | Пересборка пустого источника с успешной фиксацией прогресса |
| Есть незавершённый курсор | Возобновление пересборки |
| Есть явный запрос | Полная пересборка независимо от change-сигналов |
| Есть watermark, источники не менялись | Ожидание |
| Есть watermark, источники изменились, граница позволяет проход | Инкремент |
| Витрина отключена или остановлена | Без вычислений и изменения watermark |

Наличие watermark определяет факт успешной инициализации потребителя.
Отсутствие строки в `dbmerge_marts` само по себе не должно принудительно
сбрасывать существующий watermark или запускать полную пересборку.

## P3-1. Витрина не регистрируется в dbmerge_marts до начала пересборки

### Текущее поведение

`MartLoop.__init__()` создаёт строки аренды через `Lease.ensure()`, но не вызывает
`_ensure_marts_row()`. Первые чтения состояния могут создать саму служебную
таблицу, но не строку витрины. Строка появляется при начале блочной пересборки,
записи курсора или явном запросе `request_rebuild()`.

Таким образом, сейчас `dbmerge_marts` фактически является ленивым хранилищем
состояния пересборок, а не полным реестром объявленных витрин. Пустая таблица
при работающем цикле возможна по текущей реализации.

### Рекомендация

Сделать регистрацию отдельным, идемпотентным этапом создания `MartLoop`:

1. Проверить параметры и нормализовать identity назначения.
2. Подготовить служебную таблицу в `self.schema` через `tracker.engine`.
3. Создать отсутствующую строку для `(destination_schema, destination_name)`.
4. Подготовить аренды и опрос, не выполняя пользовательский расчёт.

Регистрацию выполнять в `MartLoop`, а не только в `MartHandler`, чтобы одинаково
работали прямое использование цикла и `handler.loop()` / `run_once()` /
`run_forever()`. Простое создание `MartHandler` без цикла при таком контракте
не обязано создавать запись; это следует явно описать в документации.

При реализации учесть порядок инициализации `_marts_table`: сейчас поле
устанавливается в `None` в конце конструктора. Не сбрасывать уже созданный
кэш таблицы после ранней регистрации. При ошибке конструктора не оставлять
принадлежащие циклу ресурсы и запись в наборе активных циклов.

Регистрация должна:

- не менять существующие флаг, токен запроса, курсор и границу пересборки;
- не записывать фиктивный watermark и не публиковать изменение назначения;
- не выставлять новый запрос полной пересборки при каждом перезапуске;
- быть безопасной при конкурентном запуске двух процессов;
- работать и для `enabled=False`, не запуская отключённую витрину;
- сохранять различие между служебной схемой и схемой бизнес-назначения;
- не предполагать наличие физической таблицы назначения: identity может быть логической.

Для создания строки можно переиспользовать `_ensure_state_row()`, проверив
его конкурентное поведение на поддерживаемых серверных СУБД.

## Разделять регистрацию, инициализацию и готовность источников

Это три разных состояния:

- **Регистрация:** витрина объявлена и видна в служебной таблице.
- **Инициализация:** выполнен первый успешный расчёт и сохранён watermark.
- **Готовность источников:** входные таблицы существуют и готовы к чтению.

Изменение источника не является надёжным индикатором его готовности: одна таблица
может уже измениться, пока другая ещё не загружена. Первоначальная сборка без
сигнала предполагает готовые источники. Если требуется ожидание начальных
выгрузок, нужен отдельный явный контракт готовности/проверка в приложении.
Отсутствие источника или ошибка расчёта не должны отмечать инициализацию успешной.

Удаление строки `dbmerge_marts` не следует документировать как API сброса.
Для принудительной сборки использовать `request_rebuild()`: он сохраняет
запрос и обновляет токен, в отличие от ручной установки одного SQL-флага.

## Рекомендуемые тесты и критерии приёмки

1. Создание `MartLoop` регистрирует одну строку назначения до первого прохода.
2. Повторное создание и два конкурентных процесса не дублируют строку
   и не перезаписывают существующие запрос/курсор/границу.
3. Источник заполнен вне трекера, change-журнал пуст, watermark отсутствует:
   первый `run_once()` выполняет пересборку и фиксирует watermark.
4. Источник пуст, change-журнал пуст: успешная первая пересборка; следующий
   проход без изменений ничего не делает.
5. Ошибка первой пересборки не сохраняет успешный watermark; повторный проход
   повторяет работу либо продолжает с последнего закоммиченного блока.
6. `enabled=False` и остановленный цикл видны в реестре, но не считают данные.
7. После успешной инициализации отсутствие изменений не запускает пересборку
   при каждом перезапуске. При новом изменении выполняется инкремент.
8. Сохранённый курсор и явный запрос работают без новых change-сигналов;
   новый запрос во время пересборки не теряется.
9. Два процесса впервые запускают одно назначение: аренда не допускает
   одновременную запись; состояние перепроверяется после получения аренды.
10. Строка `dbmerge_marts` отсутствует, но watermark есть: регистрация
    восстанавливает строку без сброса watermark и без лишней пересборки.
11. Служебная схема и схема назначения различаются, источники из нескольких
    схем: identity, прогресс и аренда не смешивают эти пространства имён.
12. Тесты регистрации и ошибок конструктора проверяют освобождение ресурсов.

SQLite подходит для базового воспроизведения, но конкурентные сценарии и
транзакционную регистрацию следует также проверить на PostgreSQL.

## P3-2. Единый язык runtime-диагностики — английский

Язык публичного проекта — английский. Рекомендуется проверить и перевести
на английский все собственные runtime-сообщения: логи всех уровней, предупреждения,
тексты исключений и сообщения примеров/обработчиков, попадающие в общий вывод.

Разделять происхождение сообщений: неанглийский текст в выводе логгера `dbmerge`
не обязательно задан библиотекой, поскольку пользовательский обработчик может
писать через `context.logger`. Проверять собственные шаблоны библиотеки и
поставляемых примеров отдельно от сообщений сторонних обработчиков.

Критерии приёмки:

- Все статические шаблоны runtime-диагностики библиотеки и поставляемых примеров
  написаны на английском; в changelog/правилах разработки закреплён этот язык.
- Перевод сохраняет уровень логирования, параметры, сведения об identity,
  аренде, watermark, блоках пересборки и исключениях; поведение не меняется.
- Тесты, проверяющие тексты сообщений, обновлены; добавлена проверка отсутствия
  кириллицы в собственных статических runtime-шаблонах.
- Не запрещать кириллицу в динамических значениях: имена объектов, данные
  пользователя и тексты ошибок внешних систем могут содержать любой язык.
  Проверка всего отформатированного лога на ASCII была бы некорректной.
- Пользовательские обработчики и интеграционные приложения проверяются отдельно;
  единый язык библиотеки сам по себе не переводит их сообщения.

Это рекомендация по унификации диагностики, а не результат полного поиска
неанглийских сообщений в исходниках текущей версии.

## P2-2. Защита source_condition от неявного декартова произведения

### Подтверждённое поведение 2.5.0

Если при загрузке из таблицы передать в `source_condition` колонки
`merge.table` вместо `merge.source_table`, SQLAlchemy добавляет целевую таблицу
в верхний `FROM` запроса источника. В результате staging получает декартово
произведение, хотя пользователь намеревался отфильтровать источник по периоду:

```sql
INSERT INTO staging (...)
SELECT source.*
FROM source, target
WHERE target.period_from = :start_date
  AND target.period_to = :end_date
```

Количество строк равно числу всех строк источника, умноженному на число строк
назначения, подходящих под фильтр. При пустом назначении источник не загружается
вовсе. Возможны высокая нагрузка, дубликаты staging и некорректный результат merge.
Первопричина — ошибка использования API в приложении; рекомендация библиотеке —
рано диагностировать опасное условие вместо выполнения неожиданного запроса.

Локальное воспроизведение вызвало установленную функцию
`dbmerge.clickhouse.insert_source_table_to_temp()` с реальными SQLAlchemy Table
и выполнением сформированного INSERT на SQLite; `_insert` заменён локальным
исполнителем. При двух строках источника и трёх подходящих строках назначения:

- ошибочный фильтр по target дал **6 фактических строк** staging и счётчик **6**;
- правильный фильтр по source дал **1 фактическую строку** и счётчик **1**;
- SQLAlchemy выдал предупреждение о cartesian product.

Локальный тест подтверждает формирование и результат ошибочного SQL, но сам
по себе не проверяет протокол ClickHouse. Первоначальная недоступность сервера
впоследствии устранена: 17 ноября 2026 выполнена отдельная read-only проверка
журнала запросов и результата SELECT на ClickHouse, описанная ниже.

В ClickHouse-ветке 2.5.0 `total_row_count` после INSERT источника берётся из
`summary.written_rows`. В общем SQL-пути используется число затронутых строк
INSERT. Проверенное воспроизведение не выявило ошибки арифметики счётчика:
аномально большое значение может отражать действительно размноженную выборку.
Серверная проверка также подтвердила совпадение `written_rows` с мощностью
ошибочной выборки в исследованном случае. Это не универсальное доказательство
семантики счётчика для любых движков, materialized views и обработчиков вставки.

### Механизм: почему фильтр изменяет FROM, а не только WHERE

`merge.source_table` представляет источник, `merge.table` — назначение.
Одинаковые имена колонок не делают колонки этих объектов взаимозаменяемыми:
SQLAlchemy Column сохраняет принадлежность конкретному selectable.

При построении SELECT исходные выбираемые колонки принадлежат source.
Если WHERE содержит прямую ссылку на target, SQLAlchemy включает target
в список источников запроса, чтобы эта ссылка могла быть разрешена.
Без условия связи возникает `FROM source, target`, то есть CROSS JOIN.
Проверка периода target ограничивает только target, но не строки source.

Пусть `S` — число всех строк источника, `T(p)` — число строк назначения,
удовлетворяющих условию периода `p`, а `S(p)` — число строк источника за период.
Тогда для показанного выше запроса:

```text
ошибочная выборка: N = S × T(p)
ожидаемая выборка: N = S(p)
```

Это формула для двух несвязанных таблиц и условия только по target;
дополнительные условия и соединения требуют отдельного анализа.
Повторяются строки источника: одна и та же строка попадает в результат
по одному разу на каждую подходящую строку target. Если source содержит
несколько периодов, они все попадают в staging, независимо от выбранного периода.

Следствия, которые важно проверять отдельно:

- `T(p) = 0`: результат пуст, даже если нужные строки source существуют;
  первая загрузка в пустое назначение может ничего не загрузить.
- `T(p) = 1`: размножение незаметно, но фильтрация source всё равно отсутствует.
- `T(p) > 1`: staging растёт кратно числу подходящих строк назначения.
- Повторный запуск зависит от текущего содержимого target; это не обязательно
  постоянный коэффициент и не обязательно экспоненциальный рост назначения.
- Последующая дедупликация может скрыть дубликаты, но не отменяет стоимость
  чтения, формирования, записи и обработки staging. Итог merge зависит от ключей,
  алгоритма сравнения и движка; один только этот дефект не доказывает порчу target.

### Серверное подтверждение ClickHouse без изменения данных

Проверены завершённые INSERT в `system.query_log`, ранее выполненные загрузчиком.
Диагностика сама выполняла только чтение, не запускала загрузку и не создавала
staging. Имена объектов и параметры подключения здесь намеренно не приводятся:
вывод относится к общему механизму библиотеки.

У источника было **4 453 строки**, распределённые между тремя периодами.
В SQL завершённых INSERT обнаружен именно несвязанный `FROM source, target`
с ограничением периода только у target. Получены следующие значения:

| Период | Строк source за период | Строк target за период при диагностике | `written_rows` завершённого INSERT | Произведение |
|---|---:|---:|---:|---:|
| A | 1 531 | 1 531 | 6 817 543 | 4 453 × 1 531 |
| B | 1 481 | 1 481 | 6 594 893 | 4 453 × 1 481 |
| C | 1 441 | 1 441 | 6 416 773 | 4 453 × 1 441 |

Для периода B дополнительно выполнен read-only `SELECT count()` над
эквивалентным CROSS JOIN: получено **6 594 893**, точно как в `written_rows`.
Для всех трёх периодов произведение текущих проверенных количеств совпало
с журналом. Это сопоставление снимка данных и истории, а не транзакционный
снимок исходных таблиц на момент каждого исторического INSERT.

В журнале у этих INSERT `read_rows = 8 906`, то есть 2 × 4 453.
Это не противоречит миллионам записанных строк: число прочитанных входных строк
не равно мощности результата соединения. Делать вывод об ошибке счётчика только
по различию `read_rows` и `written_rows` нельзя.

К моменту диагностики staging-таблицы были удалены, поэтому прямой `count()`
исторической staging выполнить было невозможно. Разделение доказательств:

1. Локально непосредственно посчитаны реальные строки staging: 6 против 1.
2. На ClickHouse журнал подтверждает миллионы `written_rows` для ошибочного SQL.
3. Независимый SELECT на ClickHouse подтверждает такую же мощность результата.
4. Исторический физический `count()` staging и соответствие конкретной строке
   прикладного лога `Temp data` отдельно не проверены.

Обычный `count()` назначения и `count()` с `FINAL` на момент проверки совпали:
4 453 строки, с тем же распределением по периодам, что у source. Это показывает,
почему нормальный размер назначения не опровергает раздувание staging, но не
доказывает ни полное равенство значений source/target, ни отсутствие иных ошибок.

**Вывод:** подтверждён дефект использования source-фильтра и отсутствие ранней
защиты от него. Данных для исправления арифметики `total_row_count` нет:
в исследованном случае большое значение согласуется с реально размноженной
выборкой и серверным журналом, а не с ошибочным умножением внутри счётчика.

### Универсальный порядок диагностики

1. Получить фактически выполненный INSERT и его SELECT, а не только исходный
   Python-фильтр. Проверить схемы, алиасы, верхний FROM и условия связи таблиц.
2. Сопоставить запросы по query ID, времени, типу завершения и staging-таблице;
   не смешивать счётчики разных запусков. Исключить из поиска саму диагностику.
3. Отдельно измерить `S`, `S(p)` и `T(p)` ограниченными read-only запросами.
   Данные могут меняться между измерениями; фиксировать время и ограничения.
4. Сравнить мощность результата SELECT с `written_rows` и прикладным счётчиком.
   Даже read-only CROSS JOIN может быть дорогим: задавать таймауты и лимиты,
   сначала оценивать произведение, не извлекать миллионы строк клиенту.
5. Если staging ещё существует, сравнить её `count()` с метриками того же INSERT.
   Учитывать движок, фоновые слияния и время измерения; не отключать cleanup
   и не повторять загрузку на production только ради доказательства.
6. Проверить DDL staging и связанные materialized views, если метрики расходятся.
   Не переносить вывод об одном пути вставки на все серверные конфигурации.
7. Отдельно проверить назначение по ключам, периодам и значениям. Счётчик строк
   сам по себе не является проверкой корректности содержимого.

### Рекомендация

Перед выполнением INSERT источника валидировать итоговый SELECT и его верхний
`FROM`. Прямая ссылка на `merge.table` в `source_condition`, добавляющая
непредусмотренный верхнеуровневый источник без связи с source, должна приводить
к понятному `IncorrectParameter` до вставки staging и любых изменений назначения.

Предлагаемый английский текст диагностики:

```text
source_condition introduces an unexpected target table into the source SELECT.
Use merge.source_table columns to filter source rows; use merge.table columns
in delete_condition to filter destination rows.
```

Проверку выполнять в общем пути и в dialect hooks, включая ClickHouse. Одного
предупреждения SQLAlchemy недостаточно: оно может быть скрыто логированием,
а ClickHouse-hook компилирует и исполняет запрос своим путём.

Не заменять автоматически target-колонки на source-колонки и не запрещать
все упоминания других таблиц: корректные `IN (SELECT ...)`, `EXISTS`, алиасы,
коррелированные подзапросы и явно связанные JOIN могут быть намеренными.
Анализировать область видимости FROM и связность итогового запроса, а не
просто искать чужие Column в дереве выражения. Для намеренного CROSS JOIN
при необходимости предусмотреть явно документированное разрешение, но не
ослаблять защиту по умолчанию.

Правильное разделение фильтров в примерах API:

```python
merge.exec(
    source_condition=(
        (merge.source_table.c['period_from'] == start_date)
        & (merge.source_table.c['period_to'] == end_date)
    ),
    delete_condition=(
        (merge.table.c['period_from'] == start_date)
        & (merge.table.c['period_to'] == end_date)
    ),
)
```

### Критерии приёмки

1. Ошибочный прямой фильтр по target отклоняется до INSERT/UPDATE/DELETE;
   тест воспроизводит прежние 2 × 3 = 6 строк и проверяет новую диагностику.
2. Фильтр по source выбирает ровно ожидаемый период; при пустом назначении
   первая загрузка также работает.
3. Корректные подзапросы, EXISTS, алиасы и явно связанные JOIN не отклоняются.
4. Проверяются одинаковые имена таблиц в разных схемах: идентичность нельзя
   определять только по имени без схемы и SQLAlchemy selectable.
5. Обычный SQL-путь и ClickHouse-hook покрыты тестами; серверный ClickHouse-тест
   сверяет `total_row_count`, `count()` staging и `written_rows` журнала запросов.
6. Документация явно различает `merge.source_table` и `merge.table`; существующие
   примеры проверены на ошибочные source-фильтры по назначению.
7. Сообщение об ошибке не содержит секретов подключения или чувствительных
   значений параметров.
8. Тестируются пустое назначение, одна и несколько подходящих строк target,
   а также несколько периодов source: проверка не должна зависеть от размера
   текущих данных или случайно успешного результата при `T(p) = 1`.
9. Тест раннего отказа подтверждает отсутствие вызова INSERT staging и операций
   изменения назначения. Защита работает и без видимого SQLAlchemy warning.
10. Интеграционный тест ClickHouse использует изолированные тестовые таблицы,
    дожидается появления записи нужного query ID в журнале и сравнивает
    метрики до очистки staging. Требуемые права и доступность query_log описаны;
    отсутствие этих прав явно отмечается как пропуск теста, а не успех.
11. Сценарий с materialized view проверяется отдельно: расхождение серверных
    метрик анализируется с учётом DDL, а не исправляется произвольным делением
    счётчика на количество строк target.

## Документация и совместимость

После реализации обновить `TRACKING_AND_MARTS.md`, описание первого запуска,
примеры и changelog. Явно предупредить: ранее новая витрина могла ждать сигнала,
теперь она начнёт полную пересборку при первом разрешённом проходе. Для крупных
витрин это изменение нагрузки; rollout требует готовых источников и планирования.

Временный обход для 2.5.0 — один раз вызвать публичный `request_rebuild()` при
подключении новой витрины. Не вызывать его безусловно на каждом старте процесса:
это превращает перезапуск в повторную полную пересборку.

Нейтральный пример для существующего SQLAlchemy Engine `engine`:

```python
from dbmerge import request_rebuild

request_rebuild(
    engine,
    ('analytics', 'sales_summary'),
    schema='service',
)
```

Здесь `service` — условная схема служебного состояния, а `analytics` — схема
назначения. Имена приведены только для иллюстрации разделения этих понятий.
При миграции с другого механизма координации нужно исключить одновременную
запись старого и нового обработчиков: независимые аренды не координируют
процессы между разными механизмами.

## Предлагаемый порядок работ

1. В библиотеке изменить условие первого запуска согласно P2-1.
2. Добавить регистрацию цикла согласно P3-1, сохранив существующее состояние.
3. Покрыть оба изменения перечисленными выше тестами, включая PostgreSQL.
4. Проверить собственные runtime-шаблоны библиотеки и примеров, перевести
   неанглийские сообщения согласно P3-2.
5. Добавить защиту source-фильтра и тесты согласно P2-2.
6. Описать изменение первого запуска, валидацию фильтров и язык диагностики в документации
   и changelog, выпустить исправленную версию.

Правки должны выполняться в исходниках библиотеки, а не в установленном
`site-packages`. Не добавлять безусловный `request_rebuild()` в каждое
приложение как постоянную замену исправлению lifecycle.
