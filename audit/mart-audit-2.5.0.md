## Контекст

Рассматриваемый общий сценарий: приложение подключает `dbmerge.MartHandler`
к уже заполненным таблицам, но новый журнал ещё не содержит записей об их
изменениях. При отсутствии watermark цикл может создать строки аренды,
но не начать первоначальную пересборку. Таблица `dbmerge_marts` при этом
может оставаться пустой.

Строки аренды с `owner = NULL` и `scope = NULL` обозначают свободные строки,
а не получение аренды. Неизменный heartbeat такой строки не означает зависание.
Явный `request_rebuild()` позволяет обойти ожидание сигнала источника.

## P2-1. Новая витрина ожидает изменения источников вместо первоначальной сборки

### Текущее поведение

В `MartLoop._run_pass()` отсутствие сохранённого watermark уже классифицируется
как полная пересборка:

```python
full_rebuild = stored_watermark is None or explicit_rebuild
```

Однако проверка изменений источников пропускается только для **явного** запроса
или сохранённого курсора:

```python
if not explicit_rebuild:
    if not full_rebuild and next_watermark <= watermark:
        return False
    if not self._sources_changed(watermark):
        return False
```

Поэтому при отсутствии watermark, курсора и запроса, а также отсутствии записей
об изменениях источников в новом журнале, цикл возвращает `False` до получения
аренды и вызова обработчика. Уже существующие данные источника сами по себе
не инициируют расчёт.

### Рекомендация

Отсутствие watermark должно означать первоначальную пересборку без зависимости
от наличия change-сигнала. Проверки «граница продвинулась» и «источники изменились»
нужны для обычного инкрементального прохода:

```python
if not full_rebuild:
    if next_watermark <= watermark:
        return False
    if not self._sources_changed(watermark):
        return False
```

Это рекомендуемая замена условия в существующем методе, а не готовый патч
всего lifecycle. Сохранить вычисление безопасной границы, получение аренды,
повторную проверку watermark/курсора/токена после получения аренды и защиту
фиксации прогресса. Не запускать запись из конструктора.

### Ожидаемая семантика

| Состояние | Действие |
|---|---|
| Нет watermark, нет change-сигналов | Первоначальная полная пересборка |
| Нет watermark, источник пуст | Пересборка пустого источника с успешной фиксацией прогресса |
| Есть незавершённый курсор | Возобновление пересборки |
| Есть явный запрос | Полная пересборка независимо от change-сигналов |
| Есть watermark, источники не менялись | Ожидание |
| Есть watermark, источники изменились, граница позволяет проход | Инкремент |
| Витрина отключена или остановлена | Без вычислений и изменения watermark |

Наличие watermark определяет факт успешной инициализации потребителя.
Отсутствие строки в `dbmerge_marts` само по себе не должно принудительно
сбрасывать существующий watermark или запускать полную пересборку.

## P3-1. Витрина не регистрируется в dbmerge_marts до начала пересборки

### Текущее поведение

`MartLoop.__init__()` создаёт строки аренды через `Lease.ensure()`, но не вызывает
`_ensure_marts_row()`. Первые чтения состояния могут создать саму служебную
таблицу, но не строку витрины. Строка появляется при начале блочной пересборки,
записи курсора или явном запросе `request_rebuild()`.

Таким образом, сейчас `dbmerge_marts` фактически является ленивым хранилищем
состояния пересборок, а не полным реестром объявленных витрин. Пустая таблица
при работающем цикле возможна по текущей реализации.

### Рекомендация

Сделать регистрацию отдельным, идемпотентным этапом создания `MartLoop`:

1. Проверить параметры и нормализовать identity назначения.
2. Подготовить служебную таблицу в `self.schema` через `tracker.engine`.
3. Создать отсутствующую строку для `(destination_schema, destination_name)`.
4. Подготовить аренды и опрос, не выполняя пользовательский расчёт.

Регистрацию выполнять в `MartLoop`, а не только в `MartHandler`, чтобы одинаково
работали прямое использование цикла и `handler.loop()` / `run_once()` /
`run_forever()`. Простое создание `MartHandler` без цикла при таком контракте
не обязано создавать запись; это следует явно описать в документации.

При реализации учесть порядок инициализации `_marts_table`: сейчас поле
устанавливается в `None` в конце конструктора. Не сбрасывать уже созданный
кэш таблицы после ранней регистрации. При ошибке конструктора не оставлять
принадлежащие циклу ресурсы и запись в наборе активных циклов.

Регистрация должна:

- не менять существующие флаг, токен запроса, курсор и границу пересборки;
- не записывать фиктивный watermark и не публиковать изменение назначения;
- не выставлять новый запрос полной пересборки при каждом перезапуске;
- быть безопасной при конкурентном запуске двух процессов;
- работать и для `enabled=False`, не запуская отключённую витрину;
- сохранять различие между служебной схемой и схемой бизнес-назначения;
- не предполагать наличие физической таблицы назначения: identity может быть логической.

Для создания строки можно переиспользовать `_ensure_state_row()`, проверив
его конкурентное поведение на поддерживаемых серверных СУБД.

## Разделять регистрацию, инициализацию и готовность источников

Это три разных состояния:

- **Регистрация:** витрина объявлена и видна в служебной таблице.
- **Инициализация:** выполнен первый успешный расчёт и сохранён watermark.
- **Готовность источников:** входные таблицы существуют и готовы к чтению.

Изменение источника не является надёжным индикатором его готовности: одна таблица
может уже измениться, пока другая ещё не загружена. Первоначальная сборка без
сигнала предполагает готовые источники. Если требуется ожидание начальных
выгрузок, нужен отдельный явный контракт готовности/проверка в приложении.
Отсутствие источника или ошибка расчёта не должны отмечать инициализацию успешной.

Удаление строки `dbmerge_marts` не следует документировать как API сброса.
Для принудительной сборки использовать `request_rebuild()`: он сохраняет
запрос и обновляет токен, в отличие от ручной установки одного SQL-флага.

## Рекомендуемые тесты и критерии приёмки

1. Создание `MartLoop` регистрирует одну строку назначения до первого прохода.
2. Повторное создание и два конкурентных процесса не дублируют строку
   и не перезаписывают существующие запрос/курсор/границу.
3. Источник заполнен вне трекера, change-журнал пуст, watermark отсутствует:
   первый `run_once()` выполняет пересборку и фиксирует watermark.
4. Источник пуст, change-журнал пуст: успешная первая пересборка; следующий
   проход без изменений ничего не делает.
5. Ошибка первой пересборки не сохраняет успешный watermark; повторный проход
   повторяет работу либо продолжает с последнего закоммиченного блока.
6. `enabled=False` и остановленный цикл видны в реестре, но не считают данные.
7. После успешной инициализации отсутствие изменений не запускает пересборку
   при каждом перезапуске. При новом изменении выполняется инкремент.
8. Сохранённый курсор и явный запрос работают без новых change-сигналов;
   новый запрос во время пересборки не теряется.
9. Два процесса впервые запускают одно назначение: аренда не допускает
   одновременную запись; состояние перепроверяется после получения аренды.
10. Строка `dbmerge_marts` отсутствует, но watermark есть: регистрация
    восстанавливает строку без сброса watermark и без лишней пересборки.
11. Служебная схема и схема назначения различаются, источники из нескольких
    схем: identity, прогресс и аренда не смешивают эти пространства имён.
12. Тесты регистрации и ошибок конструктора проверяют освобождение ресурсов.

SQLite подходит для базового воспроизведения, но конкурентные сценарии и
транзакционную регистрацию следует также проверить на PostgreSQL.

## P3-2. Единый язык runtime-диагностики — английский

Язык публичного проекта — английский. Рекомендуется проверить и перевести
на английский все собственные runtime-сообщения: логи всех уровней, предупреждения,
тексты исключений и сообщения примеров/обработчиков, попадающие в общий вывод.

Разделять происхождение сообщений: неанглийский текст в выводе логгера `dbmerge`
не обязательно задан библиотекой, поскольку пользовательский обработчик может
писать через `context.logger`. Проверять собственные шаблоны библиотеки и
поставляемых примеров отдельно от сообщений сторонних обработчиков.

Критерии приёмки:

- Все статические шаблоны runtime-диагностики библиотеки и поставляемых примеров
  написаны на английском; в changelog/правилах разработки закреплён этот язык.
- Перевод сохраняет уровень логирования, параметры, сведения об identity,
  аренде, watermark, блоках пересборки и исключениях; поведение не меняется.
- Тесты, проверяющие тексты сообщений, обновлены; добавлена проверка отсутствия
  кириллицы в собственных статических runtime-шаблонах.
- Не запрещать кириллицу в динамических значениях: имена объектов, данные
  пользователя и тексты ошибок внешних систем могут содержать любой язык.
  Проверка всего отформатированного лога на ASCII была бы некорректной.
- Пользовательские обработчики и интеграционные приложения проверяются отдельно;
  единый язык библиотеки сам по себе не переводит их сообщения.

Это рекомендация по унификации диагностики, а не результат полного поиска
неанглийских сообщений в исходниках текущей версии.

## Документация и совместимость

После реализации обновить `TRACKING_AND_MARTS.md`, описание первого запуска,
примеры и changelog. Явно предупредить: ранее новая витрина могла ждать сигнала,
теперь она начнёт полную пересборку при первом разрешённом проходе. Для крупных
витрин это изменение нагрузки; rollout требует готовых источников и планирования.

Временный обход для 2.5.0 — один раз вызвать публичный `request_rebuild()` при
подключении новой витрины. Не вызывать его безусловно на каждом старте процесса:
это превращает перезапуск в повторную полную пересборку.

Нейтральный пример для существующего SQLAlchemy Engine `engine`:

```python
from dbmerge import request_rebuild

request_rebuild(
    engine,
    ('analytics', 'sales_summary'),
    schema='service',
)
```

Здесь `service` — условная схема служебного состояния, а `analytics` — схема
назначения. Имена приведены только для иллюстрации разделения этих понятий.
При миграции с другого механизма координации нужно исключить одновременную
запись старого и нового обработчиков: независимые аренды не координируют
процессы между разными механизмами.

## Предлагаемый порядок работ

1. В библиотеке изменить условие первого запуска согласно P2-1.
2. Добавить регистрацию цикла согласно P3-1, сохранив существующее состояние.
3. Покрыть оба изменения перечисленными выше тестами, включая PostgreSQL.
4. Проверить собственные runtime-шаблоны библиотеки и примеров, перевести
   неанглийские сообщения согласно P3-2.
5. Описать изменение первого запуска и язык диагностики в документации
   и changelog, выпустить исправленную версию.

Правки должны выполняться в исходниках библиотеки, а не в установленном
`site-packages`. Не добавлять безусловный `request_rebuild()` в каждое
приложение как постоянную замену исправлению lifecycle.
