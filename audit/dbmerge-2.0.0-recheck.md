## Подтверждённые незакрытые замечания

Идентификаторы DB-* сохранены из старого отчёта, чтобы замечания можно было
сопоставлять между версиями. Приоритеты ниже отражают текущую оценку, а не
автоматически наследуют прежние P0/P1.

### DB-08, P1: поле поздней строки `list[dict]` теряется

`_get_fields_from_list_of_dict()` определяет проекцию по первой строке:

```python
data = [{'id': 1, 'a': 'first'},
        {'id': 2, 'a': 'second', 'b': 'lost'}]
```

SQLite merge успешно завершается; в созданной таблице только `id, a`, значение
`b` не сохраняется. Требуется валидация схемы всех строк до DDL/DML либо явно
заданный контракт объединения полей. Текущая потеря не сообщается пользователю.

### DB-09, P1: дубликаты названий колонок pandas теряют первое значение

```python
pd.DataFrame([[1, 'first', 'second']], columns=['id', 'value', 'value'])
```

В SQLite сохраняется `(1, 'second')`. **Уточнение старого отчёта:** pandas 3.0.5
выдаёт `UserWarning` при преобразовании, поэтому в этом окружении потеря не
полностью беззвучная. Но merge всё равно успешен и не отклоняет неоднозначный
вход. Нужна явная проверка `data.columns.is_unique` до преобразования/DDL.

### DB-07, P1: source-table пытается обновлять generated-колонку

Для source и target со схемой
`(id INTEGER PRIMARY KEY, a INTEGER, doubled INTEGER GENERATED ALWAYS AS (a*2) STORED)`
и source-строкой `(id=1, a=3)` SQLite выдаёт
`OperationalError: cannot UPDATE generated column "doubled"`, даже при пустой target.
`_get_fields_from_source_table()` исключает только audit timestamp-поля;
`_update_not_matching_data()` включает generated target-поле в UPDATE.
Это новое локальное воспроизведение старого замечания, ранее описанного для PostgreSQL.

### DB-06, P2: ограничение UNIQUE-переходов подтверждено

Target `(1, 'A'), (2, 'B')`, `UNIQUE(code)`, source `(1, 'B')`,
`delete_mode='delete'`: UPDATE выполняется до DELETE и получает `IntegrityError`.
Это воспроизводится и с `commit_all_steps=False`. Конечный снимок допустим, но
текущий алгоритм не может применить его таким порядком. Сначала зафиксировать
ограничение/нужный preflight. Перестановка DML требует отдельного решения о FK,
побочных эффектах и границах commit; сама по себе транзакция проблему не решает.

### DB-12, P2: cleanup скрывает первичную ошибку и пропускает close

Fault injection в `_insert_data_to_temp` (`PRIMARY_FAILURE`) и `_drop_temp_table`
(`CLEANUP_FAILURE`) даёт наружу второе исключение. Первое остаётся в `__context__`,
но после `exec()` `conn.closed == False`, `merge_finished == False`. При проверке
ресурсы затем закрывались явно. Это воспроизведение управления исключениями,
а не заявление о частоте реальных ошибок DROP. Аналогичный порядок есть в `__exit__`.
COPY-патч не устраняет общий дефект: нужен гарантированный close и сохранение
первичного исключения при отказе cleanup.

### DB-13, P2: описание времени и SQL по-прежнему шире реализации

Проверено по коду и документации, без повторения старого latency benchmark:
`exec()` складывает четыре таймера, а `DOCUMENTATION.md` называет `total_time`
временем всей операции. DDL, commit, rollback, cleanup туда не входят.
`*_sql = str(statement)` — представление SQLAlchemy statement, не запись
фактического SQL и bound parameters драйвера. Сначала уточнить документацию;
новые метрики и переименование API не следуют автоматически из этого замечания.

### T-04, P1: тест bulk parity принимает неполный результат

`tests/test_all.py::_assert_same_rows` проверяет `len(first) == 3`, затем идёт
по `zip(first, second)`. Отдельная проверка самой функции показала: при трёх
исходных строках второй набор длиной **0, 2 или 4** принимается без ошибки.
Нужны равенство длин обоих наборов и наборов колонок перед сравнением значений.

Это ограничивает силу зелёных bulk parity-тестов, включая восемь прогнанных
с патчем. Приложенный патч тоже пользуется этим helper и его не исправляет.

## Статусы остальных старых замечаний

«Изменено в коде» ниже не означает новый live-прогон всех перечисленных СУБД.

| ID | Статус на 2.0.0 | Основание / границы |
|---|---|---|
| DB-01 | Исходная причина устранена в коде | `_adapt_types_to_dialect()` заменяет inferred Numeric без precision на Double для MySQL/MariaDB/MSSQL/DuckDB. Явные `data_types` сохраняются; серверный round-trip здесь не выполнялся. |
| DB-02 | Частично устранено, остальное — контракт | Inferred datetime на MySQL/MariaDB → `DATETIME(6)`, naive MSSQL → `DATETIME2`. Timezone-ограничения описаны в документации; это не обещание сохранения offset на всех СУБД. |
| DB-03 | Прежняя причина устранена в коде | MSSQL не включён в `TEMPORARY_STAGING_DIALECTS`: создаётся обычная staging-таблица. Прежний запрет любого SQL Server merge нельзя переносить на 2.0.0. Остались гипотезы bulk fallback из задачи 5. |
| DB-04 | Прежняя генерация ключа устранена в коде | `_create_table` и `_create_temp_table` явно задают `autoincrement=False`; staging копирует имя/тип без Identity/Sequence/Computed. Это не доказывает поддержку произвольных generated-колонок существующей target. |
| DB-05 | Прежняя причина устранена в коде | Inferred non-key строка MySQL/MariaDB → LONGTEXT; строковый key без длины отклоняется. Явный `String()` остаётся ответственностью вызывающего кода. |
| DB-10 | Исправлено для исходных сценариев | `_check_given_types()` обновляет `data_fields` только для source-полей; `test_data_types_for_managed_field` проходит на SQLite/DuckDB. |
| DB-11 | Исходный сценарий больше не воспроизводится | Создание target идёт через `self.conn`; локальный merge `:memory:` + NullPool вставил одну строку. Новое соединение NullPool всё равно имеет отдельную in-memory БД — это не общий shared-memory режим. |
| DB-14 | Исходные сценарии отклоняются domain errors | Проверки source_schema, конфликтующих managed-ролей и bool параметров есть; соответствующие тесты проходят на SQLite/DuckDB. Это не исчерпывающая валидация всех входов. |
| T-01 | Исправлено в коде | Вторая функция переименована в `test_update_condition_version_guard`; обе функции участвуют в текущем suite. |
| T-02 | Исправлено в коде | Работа с `result` в `measure_perf.py` находится внутри main guard; прежнего обращения к неопределённому имени при импорте нет. |
| T-03 | Старое утверждение устарело, покрытие неполно | В suite теперь есть `pytest.raises` и негативные проверки API. DB-07/08/09/12 и полнота bulk parity всё ещё требуют регрессии. |
| N-01 | Поведение воспроизведено; не доказан баг текущего контракта | `update_condition=False` оставляет строку `(1, 'old', deleted=1)` без изменений. Сейчас документация прямо говорит, что неподходящие строки остаются нетронутыми. Отдельный reset изменил бы этот контракт. |
| N-02 | Исправлено | `_check_key()` запрещает mark-поле в ключе через `NoKeyError`; это отличается от предложенного в старом отчёте `IncorrectParameter`, но защищает ключ. Регрессионный тест есть. |
| N-03/N-04 | Риск конфигурации, не новая потеря вне контракта | Назначая поле `delete_mark_field`, вызывающий код разрешает записи 0/1. Документация требует отдельную колонку-флаг. Нельзя автоматически запрещать её значения без решения об API. |
| N-05 | Воспроизведено; уточнение документации | Входной `deleted=None` сохраняется как SQL NULL. Документация разрешает supplied value «as-is»; фразу «active never NULL» стоит явно ограничить auto-managed путём. |

Исторические результаты Bandit/pip-audit, упоминания CVE и широкие NO-GO из
HTML/DOCX не перепроверялись. Они не подтверждают ни наличие актуальной
уязвимости, ни отсутствие известных уязвимостей в нынешних зависимостях.

## Приёмка COPY-патча

1. Применимость к checkout подтверждена, исходный patch-файл не изменён.
2. С помощью реальной SQLite `Connection` и подменённого `_copy` проверено,
   что патч регистрирует SQLAlchemy-транзакцию до вызова драйвера. Поведение
   PostgreSQL после серверной ошибки, класс обёрнутого исключения, invalidation
   соединения и CockroachDB транзакции этим экспериментом не проверены.
3. Локально на SQLAlchemy 2.0.54 обработчики JSONB у всех трёх PostgreSQL-драйверов
   уже сериализуют JSON. Для `dict`, `list`, `None`, `JSON.NULL`, `sqlalchemy.null()`
   при обоих `none_as_null` Arrow и stdlib csv дали одинаковый CSV до/после патча.
4. Для SQLAlchemy 2.1.6 причина отсутствующего процессора подтверждается
   [исходником JSON.bind_processor](https://github.com/sqlalchemy/sqlalchemy/blob/rel_2_1_6/lib/sqlalchemy/sql/sqltypes.py#L2743)
   и [флагом диалекта psycopg](https://github.com/sqlalchemy/sqlalchemy/blob/rel_2_1_6/lib/sqlalchemy/dialects/postgresql/psycopg.py#L349).
   Это анализ исходников другой версии, **не локальный прогон 2.1.6**.
5. Требуется усилить тесты по задаче 1: проверять факт COPY, содержимое таблиц,
   SQL/JSON NULL и custom serializer; запускать обе CSV-ветки, оба режима commit,
   разные типы datetime. Отсутствие сообщения о fallback не доказывает вызов COPY.
6. Общий `_json_processors` вызывается также DuckDB и обоими MSSQL-загрузчиками.
   Утверждение «затронут только PostgreSQL» было бы неверным описанием области
   возможной регрессии. Приёмка нуждается и в этих проверках.

## Как повторить локальную часть

Из корня репозитория, в окружении с версиями из таблицы (CSV-пробы требуют
Python 3.12+, а весь скрипт — pandas, pyarrow и три PostgreSQL-драйвера):

```bash
PYTHONPATH=src .venv/bin/python audit/recheck_2_0_0.py
```

Скрипт создаёт только SQLite in-memory БД, выводит наблюдения JSON и не требует
серверов. `COPY-transaction-mock` использует подмену вызова драйвера;
`T-04-parity-helper-second-row-count` проверяет helper на подставных результатах.
Это диагностические воспроизведения, **не suite с ожидаемым зелёным статусом**:
исключения отдельных проб записываются как `probe_error`, их нельзя игнорировать.

В отдельной тестовой копии с подготовленной `data/sample_data.sqlite`:

```bash
DBMERGE_TEST_ENGINES=sqlite,duckdb PYTHONPATH=src python -m pytest tests/test_all.py -q -rs
git apply --check audit/dbmerge-2.0.1-fixes.patch
# Следующая команда относится только к копии, где проверяется кандидат патча.
git apply audit/dbmerge-2.0.1-fixes.patch
DBMERGE_TEST_ENGINES=sqlite,duckdb PYTHONPATH=src python -m pytest tests/test_all.py -q -rs -k bulk_load_stores_what
```

Все серверные прогоны и решения об изменении поведения перечислены в
[плане задач](dbmerge-2.0.0-review-tasks.md). Перепроверка аудита сама по себе
не означает готовность версии 2.0.1 к публикации.
